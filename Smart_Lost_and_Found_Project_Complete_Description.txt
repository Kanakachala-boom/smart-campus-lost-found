============================================================
2. PROBLEM STATEMENT
============================================================

In colleges and other institutions, students frequently lose personal
belongings such as ID cards, wallets, keys, books, electronic devices,
certificates, bags, and other valuables.

Currently, lost-and-found management is often handled through informal
methods such as:
- Asking friends or classmates
- Posting messages in WhatsApp groups
- Informing security staff
- Checking notice boards
- Manually maintaining lost-and-found registers

These methods are inefficient because information becomes scattered,
difficult to search, and may not reach the person who actually lost the
item.

There is therefore a need for a centralized digital system that allows
users to report lost and found items, search for matching items, and
communicate regarding their recovery.


============================================================
3. PROPOSED SOLUTION
============================================================

The proposed Smart Lost and Found Management System is a centralized
platform for managing lost and found belongings within a college or
institution.

The system allows users to:
1. Register and log in.
2. Report an item as LOST.
3. Report an item as FOUND.
4. Upload an image of the item.
5. Provide details such as:
   - Item name
   - Category
   - Description
   - Location
   - Date/time
   - Identifying characteristics
6. Search and filter reported items.
7. Find potentially matching lost/found reports.
8. Contact the person associated with a matching item through the
   appropriate workflow.
9. Submit a claim for an item.
10. Allow an administrator to verify and manage reports and claims.

5. IMPORTANT NOTIFICATION REQUIREMENT
============================================================

Notifications must be USER-SPECIFIC.

Only the user who is directly relevant to a particular event/match
should receive that notification. There should be NO global notification
where every registered user receives a potential-match notification.

Example:

Student A reports:
- Lost: Black wallet
- Location: Canteen
- Date: 30 Aug

Student B reports:
- Found: Black wallet
- Location: Canteen
- Date: 30 Aug

If the matching system identifies a potential match:

Student A receives:
"Potential match found for your lost item: Black wallet."

Student B should NOT receive a general potential-match notification.

If someone submits a claim for Student B's found item, Student B can
receive an event-specific notification such as:
"Someone has submitted a claim for the item you reported."

All unrelated users receive no notification.

Implementation concept:

Notification
- notification_id
- user_id
- message
- type
- item_id
- is_read
- created_at

Every notification must be associated with a specific user_id.

6. KEY FEATURES
============================================================

6.1 User Registration and Login
- Name
- Student/Staff ID
- Email
- Phone number
- Password
- Secure authentication

6.2 Lost Item Reporting
A user can create a lost-item report containing:
- Item name
- Category
- Description
- Location
- Date/time
- Identifying characteristics
- Image (if available)

Example:
Item: Black Wallet
Category: Personal Accessories
Location: College Canteen
Date: 28 August 2026
Description: Black leather wallet containing college ID card.

6.3 Found Item Reporting
A user who finds an unidentified item can report:
- Item name
- Category
- Description
- Location
- Date/time
- Image
- Other relevant details

Example:
Item: Bluetooth Earbuds
Location: Library – 2nd Floor
Date: 28 August 2026
Description: White earbuds found near a study table.

6.4 Smart Matching
The smart component compares lost and found reports using factors
such as:
- Item category
- Item name
- Description
- Location
- Date/time
- Colour
- Brand
- Other identifying characteristics
- Image, if implemented

The system generates a match score or ranks potential matches.

6.5 Search and Filtering
Users can search/filter using:
- Item name
- Category
- Location
- Date
- Status

Possible categories:
- Electronics
- Documents
- Accessories
- Books
- Bags
- Keys
- Other

Possible locations:
- Library
- Canteen
- Classroom
- Parking area
- Hostel
- Laboratory
- Auditorium

6.6 Claim and Verification
To prevent false claims, users should provide identifying information
that was not publicly displayed in the report.

Possible verification details:
- Unique marks
- Model
- Case details
- Contents
- Serial/identification information
- Other private identifying characteristics

A claim should be accepted only after appropriate verification.

6.7 Item Status
Lost item lifecycle:
Lost -> Potential Match -> Claimed -> Returned

Found item lifecycle:
Found -> Potential Match -> Claimed -> Returned

6.8 Notifications
Notifications are user-specific and event-specific:
- Potential match notification to the relevant lost-item owner
- Claim notification to the relevant finder
- Verification/result notification where appropriate
- Return/status notification where appropriate

6.9 Admin Module
Admin can:
- View users
- View lost reports
- View found reports
- Remove inappropriate/fake reports
- Verify claims
- Manage reports
- Mark items as returned
- Manage suspicious reports/accounts
- View statistics


============================================================
7. SMART MATCHING DETAILS
============================================================

The system should not be presented as only a CRUD website. The main
smart component is the automated lost-found matching mechanism.

Instead of:
"User manually searches every found item."

The system does:
"Lost report -> automated matching -> ranked potential matches ->
user-specific notification -> verification"

Possible implementation levels:

LEVEL 1 - Basic:
- Category matching
- Location matching
- Date/time matching

LEVEL 2 - Better:
- Description similarity
- Keyword matching
- Weighted match score

LEVEL 3 - Advanced:
- Image-based similarity / computer vision

For a 5th-semester minor project, Level 1 + Level 2 is practical.
Level 3 can be an optional enhancement depending on time and team
capability.

Example:

Lost:
Black Samsung wallet
Lost near Canteen
28 August

Found:
Black wallet
Found near Canteen
28 August

The system identifies this as a high-probability match.


============================================================
8. IMAGE-BASED MATCHING (OPTIONAL ADVANCED FEATURE)
============================================================

If implemented, uploaded images of lost/found objects can be compared
using image similarity.

Example:
Lost item image <-> Found item image

The system calculates visual similarity and identifies possible
matches.

IMPORTANT:
Image matching should be treated as assistance, not proof of ownership.
Final ownership should still require verification.

15. SECURITY AND PRIVACY
============================================================

Important design principles:
- Passwords must be stored securely as hashes, never plain text.
- JWT should be used for authenticated API access.
- Users should only access/update records they are authorized to access.
- Notifications must be tied to user_id.
- Sensitive identifying details should not be publicly exposed.
- Claim verification should protect against false ownership claims.
- Admin operations should require appropriate authorization.

19. SHORT PRESENTATION DESCRIPTION
============================================================

Our project is a Smart Lost and Found Management System designed for
colleges. It provides a centralized platform where students and staff
can report lost or found belongings. The system intelligently compares
item details such as category, description, location, date, and
optionally images to identify potential matches. Users are notified
only when they are directly relevant to a match or event, while a claim
and verification mechanism helps ensure that belongings are returned
to their rightful owners.

Technology stack:
- Frontend: React.js
- Backend: FastAPI + Python
- Database: MySQL
- API: REST API
- Authentication: JWT
- Matching: Python-based intelligent matching
- Notifications: User-specific notification system
